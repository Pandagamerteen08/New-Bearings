# Privacy Policy

## 1. Introduction

This document describes the privacy principles intended to guide New Bearings.

New Bearings is an early-stage learning application. Its actual data practices
depend on the software version and the features that have been implemented.

This document must be reviewed and updated before any public release that
collects, transmits, or otherwise processes personal information in a material
way.

## 2. Scope

This policy concerns the New Bearings application and project-controlled
services, if any.

Third-party services may operate under separate privacy policies and terms.

The presence of a feature in the roadmap does not mean the feature currently
exists or collects information.

## 3. Information that may be involved

Depending on implemented functionality, the application may handle:

- Learning content and exercise responses.
- Learning progress and review state.
- Interface and accessibility preferences.
- Application settings.
- Technical error information.
- Information necessary to provide a feature explicitly requested by the user.

This list describes possible categories, not a verified inventory of current
collection.

The project should maintain an accurate inventory as implementation develops.

## 4. How information may be used

Where the relevant functionality exists, information may be used to:

- Present lessons and exercises.
- Preserve learning progress.
- Apply user-selected preferences.
- Recover from errors.
- Improve reliability.
- Provide a user-requested feature.

Information should not be used for unrelated purposes without an appropriate
basis and clear disclosure.

## 5. Local processing and storage

The application is intended to support learning workflows, but the exact
storage location and mechanism must be confirmed from the implementation.

Local storage does not automatically mean that information is encrypted,
backed up, or inaccessible to other software running under the same account.

The project should document which records are stored and how users can manage
them once the relevant features are available.

## 6. Network transmission

No general claim is made here that the application never communicates over
a network.

Any implemented network-dependent feature should document its purpose,
the categories of information transmitted, and the service receiving it.

The application should avoid undisclosed telemetry and unnecessary transfers.

## 7. Personalization

Personalization is intended to be user-controlled and should not require a
medical diagnosis.

The project should avoid collecting sensitive information merely to infer
preferences that users could select directly.

Any future feature that uses sensitive data requires careful review before
implementation.

## 8. Sharing and disclosure

The project should not sell personal information as a default business practice.

Information may be shared with a third party only where there is an appropriate
purpose and legal basis, such as providing a clearly requested service or
meeting a legal obligation.

The actual sharing arrangements must be documented before such processing
begins.

## 9. Retention

Retention periods should reflect the purpose of each data category.

Information should not be retained indefinitely without a justified reason.

Where deletion is supported, the project should explain what is deleted and
any limitations involving backups, caches, logs, or external services.

## 10. Security

The project should use reasonable safeguards appropriate to the data and
implementation.

No software or storage system can be guaranteed completely secure.

Security practices and limitations should be documented accurately, without
claiming certifications or controls that have not been verified.

## 11. Children's privacy

The intended audience and applicable legal obligations must be assessed before
public distribution.

If the application is directed to children or knowingly processes children's
personal information, additional requirements may apply depending on the
jurisdiction and service model.

This document does not claim that the application has completed a formal
children's privacy compliance assessment.

## 12. User choices and requests

As relevant features become available, users should receive clear information
about the controls available for accessing, correcting, exporting, or deleting
their information.

The available controls depend on the actual implementation and applicable law.

A request should not be represented as completed until the responsible process
has actually completed it.

## 13. Third-party services

External services, libraries, or distribution platforms may have independent
data practices.

Review the applicable policies when using those services.

The project should identify material third-party processing before release
where required.

## 14. Changes to this policy

This policy may be revised as the application changes.

Material changes should be reflected in the published version and communicated
through an appropriate channel where required.

The policy in effect for a particular release should be identifiable.

## 15. Contact

Use the project's currently published contact or issue-reporting channel for
privacy questions.

Do not assume that a private reporting channel exists unless the project
explicitly provides one.

## 16. Important limitation

This is a preliminary project privacy policy, not legal advice or a certification
of compliance with any privacy law.

Before a public release involving personal data, review this document against
the actual product behavior, operating model, jurisdictions, and applicable
legal requirements.
